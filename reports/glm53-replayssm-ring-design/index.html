GLM5.3 ReplaySSM Ring Buffer 设计方案

本文把 xLLM 当前实现与 SGLang KDA MTP、vLLM ReplaySSM、vLLM-Ascend NPU 适配逐项对照，并给出可以审查、分阶段实现和回滚的 ring buffer 方案。核心结论先写清：当前 xLLM 是固定 4 行窗口暂存，不是真正的循环 ring；下一步优先复用 SGLang 的 MTP 事务语义和 fused ring write，暂不把 vLLM 的周期性 flush 直接搬到 MTP。

1. 审查结论

现状：xLLM 已经有 ReplaySSM 的 fold 和 stage 算子，但没有真正的 circular ring。每个请求槽位只分配 raw_key/raw_value/gate/beta 的 4-token 暂存窗口，提交后立即把已接受前缀 fold 回持久 state；pending 只是有效性标记，没有 head/tail、cursor、base 或周期性 flush。
已实现TileLang AOT 的 fold/stage + Python MTP 调用；first KDA layer 批量 fold all layers。
4 rows当前窗口容量等于 GLM5 MTP=3 的 verify width，不支持跨 verify 保存未提交数据。
SGLangKDA 也是 fold-every-commit；其关键性能点是 recurrent verify 内直接写 ring。
vLLM16-token 真循环 ring + output-only periodic flush，但明确拒绝 speculative decoding。

因此“需要不要 ring”要拆成两个问题：第一，是否需要一个按 token 位置管理的 raw-input window；答案是需要，SGLang 的 MTP 方案已经证明这是正确语义。第二，是否现在就需要 vLLM 那种跨多个 decode step 的周期性 circular flush；对 GLM5 MTP，答案是暂不直接做，因为 verify 结果在 commit 前可能被拒绝，事务边界与普通单 token decode 不同。

推荐决策：先把 xLLM 的 4 行暂存升级成“有明确 cursor/valid_len 的窗口 ring 接口”，再把 ring write 融入 NPU recurrent verify，去掉独立 stage 和 contiguous()。只有当这条路径完成事务语义和性能验证后，才评估容量 16/32 的周期性 flush。

3. xLLM 当前实现到底做了什么

当前代码位于 xllm/python/attention/npu_paged_attention.py:84 附近。每层每个物理 state slot 分配：

raw_key   : [num_slots, 4, H, 128]       bf16
raw_value : [num_slots, 4, HV, 128]      bf16
gate      : [num_slots, 4, HV, 128]      bf16
beta      : [num_slots, 4, HV]            bf16
pending   : [num_slots]                   int32
  1. verify 开始：根据接受长度和 pending 计算每个请求需要从 raw window fold 的历史 token 数；同一批次的 prior_lengths 在 Python 侧缓存，避免每一层重复计算。
  2. 第一层：收集所有 KDA 层的 state/raw tensors，调用一次 torch.ops.xllm_ops.kda_replayssm_fold_all；如果 ABI 不支持全层批量，则按层调用。
  3. recurrent verify：调用外部 recurrent_kda，使用已提交 state 作为初始状态，设置 output_final_state=False, inplace_final_state=True。
  4. 写入 raw window：多序列路径调用 kda_replayssm_stage；单序列路径用四个 index_copy_。这就是当前主要的额外 launch/copy 成本。
  5. slot reuse：通过 slot_owners 识别物理槽位换请求，并跨层清零 pending；但当前没有 generation、cursor 或环覆盖保护。
不能把它称为完整 ring：写入位置始终是窗口内的固定行，提交后下一轮重新从第 0 行开始；没有 (base + t) % capacity，也没有在覆盖前判断“未提交数据是否仍有效”。

已有 fold/stage 的 Python fake、C++ schema、TileLang wrapper 和 CMake AOT 注册，位置分别是 xllm/python/kernels_npu/_custom_op.py、xllm/core/kernels/npu/npu_ops_library.cpp、xllm/core/kernels/npu/tilelang/*replayssm*。这为下一步扩展接口提供了落点，不需要重新设计算子注册链路。

关键差异

  • SGLang 解决的是 MTP 事务问题：verify 产生的 token 先保存 raw 输入，只有被接受的前缀才从 committed checkpoint 精确 fold；拒绝的尾部不进入 state。它叫 ring，但当前 KDA 文件明确说明没有 circular ring / periodic flush。
  • vLLM 解决的是长 decode 的 state materialization 成本：state 每隔 16 token 才完整 flush，中间用缓存的 x/dt/B 做 output-only 更新。因此它的 cursor、flush、scratch 设计不能直接套到 MTP。
  • vLLM-Ascend 的可复用点是接口和 slot 生命周期：tracker 随请求 slot swap/reorder，metadata 需保持 graph-safe；不能从它推导出 NPU ring kernel 已存在。

5. 建议的目标设计

目标是保留 SGLang 的正确性边界，吸收 vLLM 的显式位置元数据和 graph-safe slot 生命周期，并在 Ascend 上把写入融合进 recurrent verify。设计分为两个模式，默认只启用模式 A。

模式 A：MTP transactional window（首选）

容量至少 1 + num_speculative_tokens，例如 MTP=3 时为 4。每次 verify 只写当前 draft window；commit 时按接受长度从 committed state 精确 fold。可以有 ring 的位置接口，但一次提交后清空 valid_len，不做跨轮覆盖。

模式 B：periodic circular flush（后续实验）

容量 16/32，保留多个已验证 decode step，写满或边界到达时 flush。只有在 verify 状态也具备事务隔离、或明确允许把输出直接写入 committed state 后才能使用。不能把 vLLM 的普通 decode 算法原样用于 MTP。

flowchart LR
  A["committed state h0"] --> B["MTP recurrent verify"]
  B --> C["raw ring write\n每个 draft token"]
  C --> D{"accept_len"}
  D -->|"0..T"| E["exact fold accepted prefix"]
  D -->|"reject tail"| F["invalidate tail only"]
  E --> A
  F --> A
  G["slot reuse: owner/generation"] --> C

必须保持的状态不变量

  1. h0 始终是当前已提交 token 前缀的 state；verify 读取它，不能读取上一次 verify 的未提交尾部。
  2. ring 中保存的字段必须与 recurrent kernel 的输入契约一致：pre-norm key、进入 recurrence 前的 value、与 gate/beta 的精度和变换顺序一致。fold 不得改用数学等价但 reduction order 不同的实现，否则会破坏 bitwise parity。
  3. commit 只 fold [0, accept_len)；[accept_len, verify_width) 必须失效，下一轮不能被当作历史输入。
  4. 物理 slot 换 request 时，owner/generation 和 valid_len 必须一起更新；任何旧请求的 raw 数据都不能被新请求看到。
  5. 同一请求在所有 KDA 层使用一致的 window metadata；fold all layers 时 layer-major stride 必须保持静态，适配 ACL graph。

6. 数据布局与算子接口建议

6.1 Ring storage

# mode A 的最小布局；L=window_capacity，默认 1+MTP
raw_key   [num_layers, num_slots, H,  L, K]   bf16
raw_value [num_layers, num_slots, HV, L, V]   bf16
gate      [num_layers, num_slots, HV, L, K]   bf16 或 fp32（与 fold contract 一致）
beta      [num_layers, num_slots, HV, L]       bf16 或 fp32
valid_len [num_slots]                          int32
write_pos [num_slots]                          int32  # mode A 可每轮从 0 开始
owner_id  [num_slots]                          int64/int32
generation[num_slots]                          int32

当前代码按 layer 分开持有 tensor；第一阶段可以保持这个 ABI，只增加 valid_len/write_pos/generation。不要在 Python 中读取设备上的 cursor 再决定分支，metadata 应作为设备 tensor 传给 AOT op，避免 graph capture 期间 host sync。

6.2 Stage / fold ABI

kda_replayssm_stage(
    key, value, gate, beta,       # [B, T, H*D] / [B, T, ...]
    state_indices,                 # [B] physical slots
    write_pos,                     # [B] int32; mode A 通常 0
    valid_len,                     # [B] int32; output or in-place
    raw_key, raw_value, gate_ring, beta_ring,
    ring_capacity                  # constexpr for AOT specialization
)

kda_replayssm_fold_all(
    states, raw_key, raw_value, gate_ring, beta_ring,
    state_indices, accept_len, valid_len, write_pos,
    ring_capacity, generation
)

如果 write_pos + t 可能跨尾部，fold 必须以 (write_pos+t) % ring_capacity 按逻辑时间顺序读取；模式 A 可以把容量固定为 verify width，保留这个接口以便后续扩大。fold 完成后把 valid_len=0, write_pos=0 写回。reject-only 的请求也必须清零 valid_len。

6.3 融合写入的推荐位置

最有希望的性能路径是扩展 Ascend 的 recurrent KDA 接口，使它在完成每个 draft token 的 gate/beta/pre-norm 后直接写 raw ring。这样可以删除当前 kda_replayssm_stage launch、四个 index_copy_ 和多序列路径的 contiguous()。这对应 SGLang 的 CACHE_RING 分支；不是把 stage 算子再做一个更大的 memcpy。

如果当前外部 recurrent_kda ABI 无法扩展，先保留 stage 作为正确性 fallback，并把融合路径做成独立 op，通过 capability/shape dispatch 选择；不能在 Python 侧假设外部 op 会写 ring。

7. 分阶段落地和性能目标

阶段实现收益预期退出条件
A：语义收紧把 4 行暂存改为显式 valid_len/write_pos/generation；stage/fold 支持逻辑位置和 wrap；保留 fold-every-commit。主要是可验证性和后续扩容，单独做可能没有 TPOT 收益。接受长度 0..4、slot reuse、wrap、混合 batch 全部和 baseline 一致。
B：融合写入在 Ascend recurrent verify 中直接写 raw k/v/gate/beta；stage 仅保留 fallback；fold 继续 all-layers batch。目标是消除独立 stage launch 和 contiguous/copy；优先改善 C1/C4 TPOT。graph replay 稳定，C1/C4 在 prefix cache 关闭、MTP=3 下有可重复收益。
C：容量实验评估 L=16/32 的 transactional pending ring；只有事务安全后再加入 periodic flush。可能降低长 decode 的 fold 频率，但 MTP 场景未必收益。证明未提交 draft 不会被覆盖；若收益不稳定，回滚到 B。

当前已测的一组参考数字只能作为阶段性方向：外部编译产物 baseline（prefix cache 关闭、TP8、MTP=3）C1 约 56.88 ms、C4 约 63.19 ms；当前 xLLM fold/stage 路径的一次干净运行 C1 约 58.65 ms、C4 约 60.21 ms。C4 有约 4.7% 改善，C1 仍略慢，说明下一步应优先减少每轮固定 launch/copy，而不是盲目扩大 ring。该数字不是最终结论，必须在同一启动参数、同一 warmup、同一 prefix-cache 关闭条件下复测。

9. 风险、未决问题和审查点

问题为什么必须先解决建议决策
外部 recurrent_kda 是否能接收 ring 输出？若不能，Python stage 仍存在，融合收益拿不到。先确认 ABI；不能扩展就做 Ascend 专用 fused verify op，保留 stage fallback。
gate/beta 到底以 bf16 还是 fp32 保存？SGLang 的 g/beta 是 fp32，而当前 xLLM 暂存是 bf16；改变精度会影响 parity。以 xLLM recurrent 输入 contract 和 bitwise reference 为准，先做双精度差分再定。
是否真的需要 16/32 行 circular ring？MTP 的 draft tail 在 commit 前不可覆盖；容量扩大不自动带来收益。模式 A 先固定 verify width；只有 benchmark 证明 fold 频率是瓶颈才做模式 C。
所有层一次 fold 的 launch 是否稳定？layer-major stride、动态层数和 graph static shape 可能冲突。保留 per-layer fallback，并在固定模型层数上优先验证 all-layer。
如何证明“算子确实被调用”？只看到 Python 分支或编译产物不代表运行时走到了 op。在 stage/fold wrapper 计数或 debug trace；E2E 日志同时记录 op path、MTP acceptance 和 kernel timing。
请审查这三项：① 是否同意先实现 SGLang 风格的 transactional window，而不是直接照搬 vLLM periodic flush；② 是否同意 fused recurrent verify 是主要性能目标；③ 是否接受 gate/beta 精度以差分结果决定，而不是为了布局直接降成 bf16。
