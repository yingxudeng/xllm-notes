Linear-State 非 Chunk 热分支与尾块缓存

设计目标是同时保留高频但非 chunk 对齐的前缀，以及请求末尾最后一个完整 KV block。第 1–9 节保留 2026-10-04 / 06 的历史设计与实测；第 10 节补充 2026-10-28 当前分支的 generation 用途、更新时机和整数边界。两部分对应不同版本，不应混读。

1. 目标与约束

KV block size 是 128，chunk size 本轮是 8192。线性状态只能从可恢复的 KV block 边界挂载；因此长度 chunk*n+r 中，只有 floor((chunk*n+r)/128)*128 之前的完整部分可以作为 checkpoint。

不承诺保存半个 KV block。例如余数小于 128 时回退到前一个完整 block，剩余 token 仍正常计算。要支持任意 token 的恢复，需要拆开 KV 游标和 linear-state 游标，当前范围不包括这项大改。

2. 当前设计

  1. 完成请求后观察：只对完整 prompt 建立观察记录。BranchAdmissionCache 以链式 KV block hash 定位条目，条目保存非 chunk 检查点的 token 数和饱和的观察次数。
  2. 热点分支准入：扫描每个 KV block 对齐的位置；位置不是 chunk 边界且同一个前缀被观察至少两次时，认定为高频分支。当前请求把这个位置加入 pending checkpoint，因此相同后继也能被保留。
  3. 尾部保存：请求结束时仍保存最后一个完整 KV block 对齐的尾部状态。pending checkpoint 按 token 数排序、去重、按顺序完成，所以同一请求可以同时保存内部热点分支和尾部。
  4. 容量保护：admission 元数据有上限并使用独立 LRU 淘汰，线性 state slot 仍由现有 LRU/占用规则回收。热点发现不改变普通 KV cache 的 ownership 规则。

实现位置：branch_admission_radix_tree.h/.cpp 独立负责压缩路径、观察计数、热点判定和 admission 元数据 LRU；linear_state_block_manager.h/.cpp 只负责线性 state 生命周期并持有该索引；composite_block_manager.cpp 负责 probe 和提交 checkpoint；sequence.h 保存有序 pending 队列。

3. 观察表到底存什么

它不是 linear state，也不是缓存 block；它是一个按前缀 hash 索引的紧凑 admission 元数据。链式 hash 已经包含完整前缀路径，所以不再复制 SGLang 那种逐 token 父子路径：

Node {
  size_t token_count;              // 这个 hash 对应的前缀长度
  uint16_t observation_count;      // 饱和计数，达到 2 即可准入
  list<XXH3Key>::iterator lru;
}

一次完整 prompt 完成后，observe_prefix_request() 从 128 token 开始逐个扫描到 prompt 尾部：

  • 跳过 chunk 边界，例如 8192、16384；这些位置已有普通 chunk checkpoint。
  • 对 128 对齐但非 chunk 对齐的位置取链式 hash。hash 已经包含此前所有 block，所以相同 key 代表相同前缀。
  • 如果 key 第一次出现，就建立一个 admission 条目并将观察次数设为 1。
  • 再次观察到同一个 key 时递增饱和计数；达到阈值 2 后即可作为高频候选。
  • 新请求 probe 时，hot_prefix_checkpoint_tokens() 找到计数达到阈值的条目，就返回最深的候选位置，并刷新该条目的 LRU 位置。
为什么使用两次观察阈值：同一个前缀被重复请求，说明它有复用价值；不要求后继 token 必须不同，因此同一后继的高频请求也能保存。只有一次观察时，直接保存会把大量一次性长请求写入昂贵的 recurrent-state cache。

这是针对线性状态 hash 链的轻量 admission 索引：hash 链隐含父路径，条目只保存长度、计数和 LRU 链，避免完整 token radix tree 的额外路径存储。上限 1<<20 时，hash、节点、map bucket 和 LRU 节点仍会占用几十 MiB，因此这是有界 host metadata，不是零成本结构。

4. Hash 必须使用 block size 域

D 节点（以及后续 Mooncake/KV store 传输）使用的前缀 key 必须对应真实 KV block 边界。当前 hash 链按 block_size=128 推进，chunk size 只决定线性状态的分段/调度，不改变 KV hash 的粒度。

对象粒度原因
KV block hash / D 节点 key128 tokens与 KV ownership、Mooncake block 传输一致
linear-state checkpoint128 的整数倍保证 KV 和 recurrent state 可共同恢复
chunked prefill8192（本轮）决定普通分段，不应改变 hash domain
小于 128 的尾巴不单独建 key只能从前一完整 block 恢复，余数重新计算

因此不要把 D 节点 hash 改成 chunk size。正确做法是保持 block-size hash，并让线性状态额外记录非 chunk 的 block-aligned checkpoint。

5. “先观察、后命中”的语义

第一次看到某个前缀时只建立观察，不会凭一次样本把状态写成热点分支。第二次观察到同一个前缀时确认它有复用价值，并提交该 checkpoint。因此三请求序列的预期是：

A: cached=0       # 冷请求，观察次数变为 1
B: cached=0       # 第二次观察，本次仍继续计算
C: cached=4096    # 后续请求命中前部非 chunk 分支
Tail-E: cached=16256   # 16383 token 请求的最后完整 KV block

API 的 cached_tokens 主要反映 KV 可见命中；linear-state tail 的恢复还要结合服务内部状态。因此验证同时看 API 计数、输出是否正常和重复请求是否稳定。

6. 必须区分两类“淘汰”

当前代码里有两个名字容易混淆、但生命周期完全不同的对象：观察表条目和真正占用 NPU block 的 prefix-cache 条目。

观察表的当前策略是否合理

作为第一阶段的 admission 过滤器，独立 compact 索引是合理的：它便宜、线程安全、只观察完整 prompt，并避免一次性把所有非 chunk 状态写入 cache。改造后元数据淘汰是确定的 LRU，不再依赖 unordered_map 的任意迭代顺序；新建路径、慢速修改路径和单键诊断查询会刷新 LRU，shared-lock 下的整条路径观察与查询不刷新 LRU，以避免在每个并发请求上引入独占锁。它仍只承担“元数据限流”，所以淘汰热点最多让后续少一次准入，不影响正确性。

它仍不是论文中的完整 FLOP-aware 淘汰。观察条目即使对应的真实 prefix-cache block 已经被普通 LRU 淘汰，也不会同步删除；此时再次识别出候选只会让 probe 查不到 block，随后正常重新计算，不影响结果，但会增加一次查找和元数据噪声。若需要严格协调，应把 admission 条目和 KV/LINEAR block 绑定成统一 entry，再实现论文的分数淘汰。

真正 prefix cache 的当前策略

PrefixCache::match()、find() 和 insert() 会把命中的节点移动到 LRU 链尾；evict() 从链头开始扫描，跳过 block.is_shared() 的仍在使用条目。它是按 block 的普通 LRU，不是按请求树节点整体淘汰，也没有 FLOP-aware 分数。

7. 和 Marconi 论文的对应关系

依据 Marconi: Prefix Caching for the Era of Hybrid LLMs（§4.1、§4.2）：

  • Admission：论文用 radix tree 记录请求历史，并根据复用历史筛选少量高价值 state。当前实现用“链式 hash 条目 + 两次观察阈值”实现同一类 admission 过滤，覆盖输入前缀的重复复用，也允许同一后继反复出现。
  • Prefill checkpoint：论文对 chunked state passing 可以落在前一个 chunk，或用额外 pass 得到精确状态。当前实现选择 KV block 对齐的状态点，不改变 D 节点 hash 域；这和论文的“安全恢复边界优先”一致。
  • Eviction：论文不是简单 LRU，而是对 radix node 计算 S(n)=recency(n)+α·flop_efficiency(n)，反复淘汰最低分节点直到腾出空间；flop_efficiency=总节省 FLOPs/所有状态占用内存。论文还会在首次淘汰后收集 5–15 倍请求样本，再搜索合适的 α。
结论：当前实现是论文 admission 思想的可控子集，不是 Marconi 的完整复刻。compact admission 条目解决了重复前缀识别和有界元数据 LRU，但 prefix cache 仍是普通 block LRU；如果目标是复现论文收益，还需要跨 KV/SSM 的统一 entry、FLOP 估计和 coordinated eviction。

2026-10-06 可观测性与生命周期回归

本轮把 admission 的运行状态接入 bvar：branch_admission_resident_entries 是所有 radix shard 的常驻条目数，branch_admission_oversized_segments 是超出单 shard 公平额度的压缩 edge 数，branch_admission_shard_entries{shard} 显示每个 shard 的占用；branch_admission_evicted_entries_total 和 branch_admission_evicted_segments_total 记录淘汰；route probe hit/miss 和 candidate block hit/miss 则分别区分“观察表路径命中”和“候选对应的真实 prefix block 存在”。radix tree 析构时会回收 gauge，避免多 DP 实例的测试或重建留下伪常驻值。

新增 8 DP、多路 1,000,003 token 的 block-level 压测。每个 DP 反复提交 8 条同一 shard 的 1M hash 路径，验证分片上限会触发 eviction，常驻条目不超过 8 * ceil((1<<20)/64)，并在实例销毁后回到测试前基线。该用例只测 host metadata 的 radix/hash 规模，不把条目数当作字节数，也不宣称完整模型 1M NPU E2E；完整模型 E2E 仍受显存与服务资源限制。容器内用同一 gtest 进程采样到峰值 VmHWM=947,968 kB，其中包含运行时和测试框架开销，不能当作 metadata 单独占用。

admission 现在只在最终 deallocate_for_sequence() 观察一次。scheduler 的 cache_for_sequence() 和 allocate 阶段仍会发布已经完成的 block，但不会把同一请求重复计数成两次观察；显式 Host/Mooncake composite 继续使用 PrefixCachePublishMode::EXPLICIT，由已有显式 Host、hierarchy prefetch 和 offload 用例验证。

decode 侧新增能力接口 supports_linear_state_restore()。普通 pool 没有 host linear restore 时，空 decode 请求不会把 KV-only prefix 挂到未初始化的 recurrent state 上，而是重新分配自己的 LINEAR slot；Hierarchy 只有在启用 linear state 且 Host LINEAR 有容量时才报告可恢复。DecodeWithoutLinearRestoreDoesNotMountKvOnlyPrefix 覆盖该边界，取消用例同时验证 pending checkpoint 在 cache/discard 两种释放路径都被清空。

9. 限制与后续观察点

  • admission 元数据有界，当前按分片访问 LRU 淘汰，不是 LFU/FLOP-aware；它保护内存，但不会保证最高频分支永久保留，分片负载不均时各分片会独立淘汰。
  • 线性 state slot 仍可能因为容量回收而丢失早期 checkpoint；这表现为缓存未命中，不影响正确性。
  • cache-on 与 cache-off 都暴露了 NPU/图执行重复性波动；发布前应固定执行确定性并保留 cache-off 对照，避免把模型波动误判为缓存回归。
  • 若要继续贴近论文，应先采集真实请求的复用次数、重算 FLOPs 和 state 内存成本，再设计跨 KV/LINEAR 的统一评分淘汰；当前 LRU 作为确定性的 metadata 上限足够稳妥。
结论：保持 D 节点/Mooncake 的 block-size hash；用链式 hash 驱动的紧凑 admission 索引准入非 chunk 热分支；尾巴按最后完整 block 保存。当前实现和本轮真实服务结果符合这一设计，GSM8K 的重复性问题需要单独治理。

10. generation：热点元数据的“重置代号”

代码时点：2026-10-28，分支 feat/glm53-linear-prefix-cache-hit-op-3，提交 0ad8a4f22。本节基于该提交的实际实现，不沿用前面历史 radix 方案的字段或计数方式。

一句话：generation 表示“当前热点表是哪一次清空之后的那一代”。它不是请求编号、命中次数或生成 token 数。它让请求知道：之前已经记过的票、之前缓存的热点停点，还能不能用于当前这张热点表。

10.1 先回答最关心的四个问题

问题当前实现的答案
干什么用？配合热点表 reset，隔离旧的请求计票标记和Sequence 停点计划。
什么时候增加？启用 prefix cache 时，BlockManagerPool::reset_prefix_cache() 清空策略表，然后对每个存在的 DP 策略执行一次 ++generation_。普通请求、命中和 token 更新不增加它。
会超过 int64 上限吗？它实际是 uint64_t，不是 int64_t。跨过 2^63 - 1 仍可正常表示；只有理论上的 uint64_t 极限需要另论，见 10.6。
是不是必须？不是 hash 命中算法的必要参数，但在当前“热点表可以 reset、请求状态可能继续存在”的契约下，需要它或等价的失效机制。不能只删字段和比较，就声称行为不变。

10.2 三个位置，不是三个独立计数器

位置 / 初始值谁拥有何时写入、用于什么
LinearPrefixPolicyState::generation_
uint64_t = 0		每个启用 admission 的 DP 各有一份这是比较时的基准代号。只在 pool 的 prefix-cache reset 中递增；与策略表一起受该 DP 的 mutex 保护。

传给 mark_linear_prefix_observed(generation)、linear_prefix_checkpoint_tokens(generation) 和 set_linear_prefix_checkpoint_tokens(..., generation) 的参数，都是把当前 DP 的代号传过去比较或盖章，不是每调用一次就把 pool 的代号加一。

SequencesGroup 为一个新请求创建共享的原子标记；它派生出的 Sequence 使用同一个标记，拷贝构造也保留共享关系。单独构造的 Sequence 在没有传入标记时自行创建。这样 cache、释放、重试以及同请求的多条分支，不会在同一代里重复贡献观察。

计划中的 token_count == 0 不是“还没算”，而是“已经算过，本轮不加额外热点停点”。因此 {0, generation, dp_rank} 也会被缓存；nullopt 才表示需要重新规划。

10.3 什么时候更新？把“递增”和“记录”分开看

BlockManagerPool::reset_prefix_cache()
  prefix cache 未启用：直接返回
  否则先 reset 各 block manager 的 prefix cache
  对每个非空 LinearPrefixPolicyState 加锁：
    policy_.reset()       → 清空 observations_ 和 LRU
    ++generation_        → 新一代

不遍历所有 Sequence，也不立即改写它们的标记或计划。
请求下一次观察 / 规划时，比较当前代号，按需重新记票 / 规划。
事件DP 的 generation_请求计票标记 / 私有计划
构造新的 pool / 重启后重建从 0 开始，不持久化新请求的标记为 UINT64_MAX，计划为空。
首次规划热点停点不变写入带当前代号和 DP 的计划，包括结果为 0 的情况。
完成 prompt，进入有效观察不变标记记录当前代号；该请求本代首次观察才向热点表记票。
同一请求再次 cache / deallocate不变标记已是同代，不重复记票。
命中 / 未命中、decode token 增长、LRU 淘汰、其他请求把前缀变热不变这些事件本身不会因为代号变化而使已有计划失效。
Sequence::reset()不变清私有计划，保留共享计票标记；下一轮可以重算停点，但不能重复给同一代投票。
当前 Sequence 改 DP不因此递增计划读取时检查 DP，不匹配就重算；共享计票标记保留。
pool 的 reset_prefix_cache()每个已启用策略的 DP 加一旧标记、旧计划不立即改写；下一次使用时因代号不同而按新一代处理。

观察入口是 BlockManagerPool::cache(Sequence*)、普通 pool 的 deallocate(Sequence*) 以及 hierarchy pool 的释放路径。还要满足：Sequence 非空、不是 graph warmup、完整 prompt 已计算，以及对应 DP 的 admission 已启用。未完成 prompt 不记票，reset 后也不会自动给所有活请求补票。

现有生产调用链不是假设：当前代码中，普通无参唤醒路径会在 engine_->wakeup(options) 成功、enable_sleep_mode 开启且 scheduler 存在时触发 reset：

APIService::do_wakeup()：没有 remote_addrs 的分支
  → LLMMaster::wakeup()
  → engine_->wakeup(options) 成功，且 enable_sleep_mode
  → scheduler_->reset_prefix_cache()
  → ContinuousScheduler::reset_prefix_cache()
  → BlockManagerPool::reset_prefix_cache()
  → policy_.reset() + ++generation_

注意分支边界：带远程权重地址的 API 分支调用 wakeup(const WakeupOptions&)，该重载本身没有上述 scheduler reset；不能笼统地说“每种 wakeup 都增加 generation”。直接 sleep、pause、resume 也不是这里的递增语句。普通持续推理若没有调用 prefix-cache reset，代号可以一直为 0；它并不随 QPS 增长。

10.4 两个用途，各看一个例子

用途 A：清表以后，活着的请求可以为新表重新贡献一次观察。假设请求 R 的共享标记初始为 UINT64_MAX，当前代号为 7：

第 7 代，R 首次完成 prompt：exchange(7) 返回 UINT64_MAX → 记一次
第 7 代，R 再次 cache / 释放 / 由同组分支进入：返回 7 → 不记
第 7 代，R 被抢占并 Sequence::reset()：标记仍为 7 → 不重复记

pool reset：热点历史被清空，代号从 7 变成 8；R 的标记仍为 7
R 后续再次满足完整 prompt 的观察条件：exchange(8) 返回 7 → 新表记一次
第 8 代，R 再次观察：返回 8 → 不记

如果只换成终身不清的 observed = true，清空热点表以后，这个活请求永远不能再为新表贡献观察。如果把 bool 放在 Sequence::reset() 里清掉，又会让同一代中的抢占重试重复投票。这就是“一次执行尝试”和“一代热点历史”不能共用一个 reset 边界的原因。

用途 B：不让旧热点表算出的停点计划跨代复用。

第 7 代、DP 0：Sequence 缓存了计划 {停在 3200, 7, 0}
pool reset：热点表清空，当前代号变成 8
下一次规划：发现 7 != 8，旧计划不再有效
查当前空热点表：得到 0，保存 {不额外停, 8, 0}

如果删除代号检查，旧的 3200 仍可能直接返回，尽管当前热点表已经没有这个决策依据。这里失效的是调度停点计划，不是根据 generation 直接选择 KV 或 LINEAR 物理块；不能把这个后果夸大成“必然读错模型状态”。

反过来，其他请求把某个前缀变热时，generation 并不会变。已有计划 0 在同一轮尝试内继续稳定复用；发生 Sequence::reset() 后清掉计划，下一轮才可能重新发现热点。这也解释了为什么有 generation 检查，仍然需要 Sequence::reset() 中的计划清理。

10.5 generation 是必须的吗？按契约判断，不按字段名判断

保留的能力 / 方案是否需要 generation代价或约束
仅讨论 hash 匹配、checkpoint 保存与恢复不是算法必需当前 generation 不参与 block hash、实际 prefix 匹配键或物理 slot ID。
当前 reset 接口允许清热点表，但请求对象可能继续存在需要它或等价的跨 reset 失效机制必须同时处理旧计票标记与旧计划；只清 policy_ 不够。
明确约束：不会运行期 reset，或 reset 时已不存在任何旧请求可以设计更简单的实现请求级共享 bool 可做去重，私有 optional 可缓存计划；但这是收窄 reset 契约，不能默认为现有系统已经保证。
去掉代号，reset 时主动遍历并清理所有旧请求字段可以替代需要覆盖运行、等待、抢占后保留的请求及同组分支；block manager 原本并不拥有所有这些对象，管理和耦合成本更高。
去掉计划缓存，每次调度重新查询热点表只能替代计划缓存的一部分作用仍要解决计票去重，并且会改变当前“同一轮计划稳定，包括 0”的约定，不是直接等价删除。
对当前 PR 的判断：保留现有 prefix-cache reset / sleep-mode 唤醒契约时，建议保留 generation。它负责本次 hot-prefix 新增元数据的生命周期，不同于已经从本 PR 撤出的 shared checkpoint 写保护修复。可以换实现，不应无条件删掉；本次只补说明，没有修改运行代码。

它也不是并发同步屏障。DP 的策略表和代号由 mutex 保护，请求标记用原子 exchange 做去重；generation 本身不等待 GPU/NPU、不管理物理块存活，也不能替代调用方在 sleep / reset 时所需的调度同步。

10.6 会超过 int64 限制吗？真实类型与理论边界

值十进制与当前代码的关系
INT64_MAX = 2^63 - 19,223,372,036,854,775,807有符号 64 位上限；不是 generation 的类型上限。
2^639,223,372,036,854,775,808已经超过 int64 上限，但仍是合法的 uint64 值。
UINT64_MAX = 2^64 - 118,446,744,073,709,551,615代号的无符号上限，同时被新请求的计票标记用作“尚未观察”的哨兵。

策略代号、共享原子标记、计划里的代号以及这几个方法的参数，当前都是 uint64_t，没有在这条链上转成 int64_t。所以跨过 INT64_MAX 不会在此触发有符号溢出。新请求标记一开始就是 UINT64_MAX，不代表服务已经 reset 了这么多次。

但不能说“数学上永远不会出问题”。当前代码没有跳过哨兵，也没有防回绕逻辑：

  1. 当 pool 的代号真的等于 UINT64_MAX 时，新请求的初始标记恰好也等于它。第一次 exchange 会返回相同值，误判为“这代已经观察过”，因而跳过新请求的观察。这是哨兵冲突，在下一次加一前就能出现。
  2. 再执行一次 ++generation_，无符号值回绕成 0。若某个旧请求状态真能跨越完整周期仍然存在，旧的 0 可能与新的 0 被误认为同代。这是代号复用问题，不是 int64 的限制。

数量级上，即使假设每秒进行一百万次全局 prefix-cache reset，达到 int64 上限也约需 29.23 万年，达到 uint64 上限约需 58.45 万年（按一年 365.25 天计算）。实际代号只随 reset 增加，且重建 pool 从 0 开始。因此这是需要说明的理论边界，不是正常持续推理的现实容量瓶颈。

不要与热点计数混淆：当前 Observation::count 是 uint16_t，pool 使用的热阈值为 2；只有小于阈值时才加一，达到阈值后饱和。命中很多次，不会把 generation 或这个热度计数无限推高。
